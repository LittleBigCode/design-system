# Component documentation page

Every component page under `examples/components/` is generated by `scripts/build-docs.mjs` from data — there is no per-component page file to hand-edit. Documenting a component means editing three places; `npm run build` renders whatever it finds into `examples/components/<slug>.html`:

1. **Registry entry** — `examples/registry/registry.ts` (intro, examples, part notes)
2. **Demo files** — `examples/registry/demos/<slug>/*.tsx` (one file per example)
3. **Playground** — `examples/registry/playgrounds/<slug>.tsx` + an entry in `examples/registry/playgrounds.ts` (powers the Workbench)

**Before writing anything, read `references/exemplar.md` (in this skill's directory).** It is a complete annotated worked example — all four surfaces of one component (Panel) documented to the house standard, plus the `PlaygroundConfig` type contract. Match its register: the field discipline, the demo realism, the sparseness. It travels with the skill, so it stays the standard even if the live Panel files drift.

The page renders: unlabeled intro (badge, name, description, intro paragraphs, import line) → **Workbench** h2 (only when a playground exists) → **Examples** h2 with one h3 subsection per example → a nested TOC (sections level 1, examples level 2). All of this is automatic; you never touch the generator to document a component.

## Step 1 — Registry entry

Fields and their jobs (don't blur them):

- `description` — a one-line tagline, ideally positioning the component against a sibling ("Card without the shadow"). Not a paragraph.
- `intro?: string[]` — one to two when-to-use paragraphs, one `<p class="docs-note">` each. Paragraph 1: what it is and when to reach for it. Paragraph 2 (optional): the one architectural fact that changes how you use it (the exemplar's: the root owns `--panel-spacing`). Skip `intro` entirely rather than padding it — the page falls back to the description cleanly.
- `examples` — each entry is **one use case backed by one demo file** (`demo: "<slug>/<file>"`). Titles name the use, not the prop ("Settings rows", not "Rows"; "Form section", not "With footer"). Descriptions say when you'd build this and name the one non-obvious mechanism in backticks.
- `parts?: Record<string, string>` — gotcha notes keyed by part name. The generator does not currently render a part index or anatomy tree from this field (that mechanism was left behind with the retired React docs app it was ported from — see `docs/adr/0003-one-generated-site-no-bundler-dependent-surface.md`), so an entry here is inert today: it type-checks but nothing reads it. Put the constraint in an `intro` paragraph or the relevant example `description` instead until a reader for `parts` exists.

Prose fields render through `escapeHtml`/`prose()` in `scripts/build-docs.mjs`, which supports **backticks only** — no markdown links, bold, or lists.

## Step 2 — Demo files

One file per example in `examples/registry/demos/<slug>/`. There is no auto-registration or orphan rendering: `build-docs.mjs` only ever renders the `examples` a registry entry lists, reading the file's source for the Code tab and importing its compiled output (`dist/docs/demos/<slug>/<file>.js`) to mount the Preview tab — so a demo file with no matching registry `examples` entry never appears anywhere. Always pair the file with a registry entry.

Conventions (full worked demos are in `references/exemplar.md`, Surface 2):

- Default-export a single component named `<Component><UseCase>` (e.g. `PanelFormSection`).
- Realistic content — real labels, plausible values, working sub-components (a footer with `Cancel`/`Save` buttons, not `<Button>Action</Button>`). The demo's code is shown verbatim in the Code tab, so it doubles as copy-paste documentation.
- **No comments.** The demo's code is shown verbatim in the Code tab and reads as copy-paste output; a non-obvious why belongs in the registry example `description`, not in the file.
- Constrain width on the demo root (`w-full max-w-sm`-style), not the preview.

Prefer extending the demo whose use case already implies a part you need to show over writing a new demo that exists to display one export.

**Choosing the example set**: cover the component's distinct *shapes of use*, not its prop matrix. The exemplar's set — Basic (self-contained summary), Settings rows (a divided list), Form section (fields + acting footer) — each answers "when would I build this?". Variant sweeps (sizes, tones) earn a demo only when the axis is the component's point. Three to five examples is the healthy range.

## Step 3 — Playground (Workbench)

Two coordinated pieces:

**`playgrounds/<slug>.tsx`** — a typed template that renders the subject with prop pass-through (`{...props}`). Render **every exported component part you reasonably can**: the Workbench's code strip is the only place a reader sees a part in isolation, so an unrendered part is effectively undocumented. Groups, labels, separators, shortcuts, submenus, badges, footers and action slots all belong in the template — a select that shows no `SelectGroup` is documenting half its grammar. Place a literal `{children}` marker for the main editable text and `{key}` markers for each entry in `texts`.

Three kinds of part stay out of the template, and each has somewhere else to be:

- **Parts the component renders itself** — `DialogContent` opens with a `DialogPortal`, `ProgressTrack` is drawn by `Progress`. Writing one into the template double-renders it.
- **A different composition** — chips mode for combobox, a group for avatar, `CommandDialog` for command. One template cannot be both, and a contrived one stops being copy-pasteable.
- **Parts that restructure the whole preview** — sidebar's header, footer, trigger, rail and inset are app-shell furniture around a static sidebar. The template caps at a readable size (one screen of code strip); overflow goes to a demo instead.

For the last two, show the part in a demo instead of a dead end in the playground — the Workbench is the *shape* documentation, and demos carry the rest.

Give the subject its accessible name with `aria-label` directly rather than an `sr-only` span plus `aria-labelledby` — the span is invisible in the preview but still prints into the generated snippet, which makes the copyable code read as boilerplate the component does not need.

**`PLAYGROUNDS[slug]` in `playgrounds.ts`** — only what cva cannot know (the full `PlaygroundConfig` type contract is at the end of `references/exemplar.md`):

- `variantsFrom` — name of the cva const; variant axes are parsed from it at build time (`scripts/build-docs.mjs`'s `extractVariants`), never listed here.
- `extras` — plain props worth exposing (`boolean`, `text`, `select`). Use `always: true` only for props the component requires.
- `children` / `texts` — editable text content with sensible defaults and short labels. Each key needs a matching literal `{key}` marker in the template's JSX.
- `note` — one sentence, only when the subject genuinely needs explaining (the exemplar's explains why `size` isn't a cva axis).

## Landing a slug the registry still filters out

The registry is filtered to what this package ships, so a component absorbed by
a batch is invisible until its entry moves **and** its demo files exist:

1. Lift its entry out of `PENDING` into `COMPONENTS` in `examples/registry/registry.ts`.
2. Write its demo file(s) under `examples/registry/demos/<slug>/`, matching every `demo` key its `examples` list names — there is no parked location to move them from; a `PENDING` entry's demo files don't exist yet until you write them (Step 2).

Skipping the second move breaks the build: `scripts/build-docs.mjs` reads
`examples/registry/demos/<slug>/<file>.tsx` for every `examples` entry the
lifted doc declares, and fails loudly if one is missing.

## Verify

1. `npx prettier --check <files you touched>` — **never** `npm run format` (it rewrites the whole repo).
2. `npm run build` — compiles the demos/playgrounds (`build:docs`) and regenerates every page (`scripts/build-docs.mjs`). It fails loudly (naming the file) if a registry `examples` entry points at a demo file that doesn't exist, or a `variantsFrom` name that doesn't resolve — that is the coverage gate.
3. `npm run serve` (port 8080), then open `examples/components/<slug>.html`: intro paragraphs render with code spans, Workbench controls work and edit the live preview, each example previews and its Code/HTML tabs match, TOC nests and its anchors scroll.
